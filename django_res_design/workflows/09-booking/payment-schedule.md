# Payment Schedule

The 3-tier payment schedule (Initial Deposit, Rental Balance, Security Deposit) attached to every booking. Generated by the booking-creation workflow; mutated by booking-modification; status-flipped manually by staff when a payment arrives offline.

## Generate 3-tier payment schedule

**ID:** `BOOKING.PAYMENT_SCHEDULE.GENERATE`
**Trigger:** Sub-workflow of `BOOKING.LIFECYCLE.CREATE_FROM_QUOTATION` and `BOOKING.LIFECYCLE.MODIFY`.
**Actor:** System.
**Legacy locus:** `Booking.razor:612-762` (computation); `ResService.cs:3252-3260` (persistence); SP `SP_GET_PAYMENTDETAILS`.

### Inputs (computed)
- `RentalPrice`, `AdjustmentValue`, `DisclountValue` `[TYPO]`, `ConciergePrice`
- `OverrideDeposit` (% — default fallback to system default if `!IsOverrideDeposit`)
- `SecurityAmount`, `SecurityDepositAmount`, `SecurityDepositType` (1=%, 2=fixed)
- `BookingDate`, `FromDate`, `BalanceDueDays` (configurable, e.g. 14)
- `PaymentMethod` (`10`=CC, `20`=BT)

### Process
1. **Decide full-payment vs 3-tier** (`Booking.razor:720-762`):
   - If `daysToArrival < BalanceDueDays` → **Full payment**: skip deposit, single line due `today+2`.
   - Else: **3-tier** as below.
2. **Compute deposit**: `CalcInterest(adjustedAmount, OverrideDeposit%)` or fixed override.
3. **Compute security deposit**: `IsSecDepAmt ? SecurityAmount : CalcInterest(RentalPrice, SecurityDepositAmount, SecurityDepositType)`.
4. **Build three `PaymentDetails`**:
   - **Deposit** — `Description="Deposit"`, `Amount=initialDeposit`, `Date=BookingDate`, `Status=AWAITING_DEPOSIT`, `PaymentMethod`.
   - **Balance** — `Description="Balance"`, `Amount=adjustedAmount - initialDeposit + ConciergePrice`, `Date=FromDate - BalanceDueDays`, `Status=BALANCE_DUE`.
   - **Sec Dep** — `Description="Sec Dep"`, `Amount=securityDeposit`, `Date=FromDate`, `Status=AWAITING_SD_DETAILS`.
5. **Persist** — for each, `SP_GET_PAYMENTDETAILS` with INSERT/UPDATE/DELETE keyed by the row's id.

### Outputs / side effects
- **DB write:** typically 3 rows in `VillaPayment` (fewer for full-payment).
- **Side effect on quote display**: `CheckoutDetail.PaymentDuesDates[]` is filtered (`Amount > 0`) and sorted (Deposit → Balance → Sec Dep) for the public-site checkout view.

### Data transformations for storage
- Currency: all amounts are in the booking's `CurrencyId`.
- Concierge included **only in balance**, and **only when `ConciergeService == 2`** (Signature tier).
- Description strings are matched on by `INTEGRATIONS.ZOHO.PUSH_QUOTATION_BOOKING` to set Zoho fields (`Initial Deposit`, `Balance Payment`, `Security Deposit`).

### Failure modes
- Concurrent modify could race against a payment recorded between recompute and save — there's no version check.

### Open questions
- Hard-coded 3-tier semantics should become configurable templates in the redesign (some bookings might want 4 tiers, some 2).
- The "full payment" shortcut needs explicit business validation — currently it just zeroes the deposit silently.

## Update payment status (record offline payment)

**ID:** `BOOKING.PAYMENT_SCHEDULE.SET_STATUS`
**Trigger:** Staff toggles "Change" checkbox on a payment line + clicks Save (`Booking.razor:374-380`).
**Actor:** Staff (after receiving payment offline).
**Legacy locus:** `ResService.cs:3426-3442`; SP `sp_update_payment_status`.

### Inputs
- For each updated payment: `Id`, new `Status`, `IsOfflinePayment` (true for staff-marked), `Description`

### Process
1. Iterate the updated payments.
2. Per row, `sp_update_payment_status @Id, @Status, @IsOfflinePayment`.

### Outputs / side effects
- **DB write:** `VillaPayment.Status` updated.
- Toast "Payment status updated successfully".

### Failure modes
- Payment not found → DB error.
- No audit trail of who marked which row paid `[AUDIT]`.

### Open questions
- The redesign should record actor + timestamp + delta on every status flip.
- Distinction between "offline payment received" and "I'm just marking this paid" is semantic — the redesign should require evidence (file upload / reference number).
