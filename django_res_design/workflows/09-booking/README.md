# 09 · Booking

Confirmed reservations. A booking is the row that locks a villa for a guest, generates the 3-tier payment schedule, requires owner approval, and tracks the operational state of the stay.

## Files

| File | Workflows |
|---|---|
| [`booking-creation.md`](./booking-creation.md) | Create booking from quotation (the "Start Booking" workflow that materialises 3-tier payments, hold→booked transition, emails, WordPress checkout link, Zoho push) |
| [`booking-modification.md`](./booking-modification.md) | Modify booking (dates, party size, override deposit, concierge), recompute payment schedule |
| [`booking-management.md`](./booking-management.md) | List bookings, view booking detail, resend booking summary |
| [`booking-confirmation.md`](./booking-confirmation.md) | Owner confirm / reject a booking, notify guest |
| [`booking-cancellation.md`](./booking-cancellation.md) | Cancel / soft-delete booking, release availability |
| [`concierge.md`](./concierge.md) | Save concierge service add-ons, request concierge payment |
| [`payment-schedule.md`](./payment-schedule.md) | Generate / regenerate the 3-tier payment schedule; record payment-status updates from staff |

## Entities touched

- `VillaBooking` — master booking record: `Id`, `QuotationNo`, `VillaId`, `FromDate`, `ToDate`, `RentalPrice`, `DepositAmount`, `OverrideDeposit`, `DepositPercentage`, `BalanceDue`, `BalanceDueDate`, `CurrencyId`, `Adults`, `Children`, `TBC` (party size To-Be-Confirmed flag), `DiscountPrice`, `AdjustmentPrice`, `ConciergePrice`, `Notes`, `InternalNotes`, `HouseRules`, `TagsInformation`, `ConciergeService` (`1` = Quintessential, `2` = Signature), `PaymentMethod` (`10` = CC pre-auth, `20` = BT bank transfer), `IsOwnerConfirmed`, `IsDepositePaid`, `IsEmailSent`, `BookingUrl` (WordPress URL slug returned from public sync), `ZohoId`, plus standard audit columns
- `VillaPayment` — payment schedule rows (typically 3 per booking): `Id`, `BookingRefNo` (→ `QuotationNo`), `Description` ("Deposit" / "Balance" / "Sec Dep"), `Amount`, `Date`, `Status`, `PaymentMethod`
- `VillaBookingConcierge` — concierge line items: `ConciergeId`, `CurrencyId`, `Price`, `Notes` (description)
- `VillaClientDetails` — guest info captured at booking time (sometimes during checkout)

## Stored procedures

- `SP_SAVE_BOOKING_INFO` — primary booking save (output `@Id`)
- `SP_GETBOOKINGDETAILSBYID` — fetch full booking + computed fields
- `SP_GET_BOOKING_DETAILS` — paginated list
- `SP_GET_PAYMENTDETAILS` — write payment schedule rows
- `sp_update_payment_status` — staff offline-payment status flip
- `sp_concierge`, `SP_BOOKING_CONCIERGE` — concierge CRUD
- `SP_CONFIRM_BOOKING` — owner confirm / reject
- `sp_delete_booking` — cancellation

## Cross-cutting notes

- **Booking reference format** is `VC{QuotationNo}` — that's the human-visible reference number. SP boundaries strip the `VC` prefix.
- **Payment method enum** (`10` / `20`) drives downstream behaviour: deposit and security-deposit handling differ depending on whether the gateway holds a card or expects bank transfer.
- **`TBC` flag**: party size may be "to be confirmed later" — booking can be created without firm guest count.
- **Zoho push happens twice on save** — once to update enquiry shape (`PushZohoEnqueireAsync`) and once to push the booking record (`PushZohoBooking`).
- **WordPress integration**: a "checkout URL" is generated by the public site and stored locally; it's how the guest pays.

## Open design questions for the Django redesign

- The data-model design (`../05-reservations.md`) plans `reservations.Booking`, `reservations.BookingHold`, `reservations.BookingEvent`, `reservations.TermsVersion`, `reservations.Concierge`. Adopt the event-row pattern so every state transition is auditable.
- Replace `VillaBooking.IsOwnerConfirmed` boolean with an explicit `OwnerConfirmation` state machine + event log.
- Decompose the payment-method int enum into a typed enum.
- The 3-tier payment schedule (Deposit / Balance / Security Deposit) is hard-coded in code branches — model it as configurable payment-schedule templates on the property.
- The "client details captured at booking time" (`VillaClientDetails`) is **separate from** the `VillaContact` master directory and **separate from** the client fields denormalised on `VillaQuotationMaster`. The redesign should unify on a single `Guest` model with snapshots taken at booking time for audit.
